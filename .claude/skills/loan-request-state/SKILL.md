# 상호대차 요청 상태 전환

상태머신은 이 프로젝트의 심장이다. 승인이나 수락 같은 판단 단계 없이, 신청 조건을 통과하면 바로 진행되고 실물에 문제가 있을 때만 발송 불가로 끝난다. 현재 전환표, 권한, 취소 사유, 진행 중 기준, 이용자 표시 단계는 `references/transitions.md`에 있다. 작업 전에 먼저 읽는다.

## 설계 원칙과 이유

- **상태머신은 Spring 없이 순수 자바로 둔다.** 전환 규칙 테스트가 수십 개여도 1초 안에 돌아야 규칙을 자주, 촘촘하게 검증할 수 있다. JPA 엔티티의 행위 메서드가 이 순수 규칙을 호출한다.
- **표에 없는 전환은 모두 거부한다.** 허용 목록 방식이어야 새 상태나 행위를 추가할 때 빠진 경우가 조용히 통과하지 않는다.
- **권한은 두 층이다.** 역할 검사는 Spring Security(8단계)가 하고, 이 요청에서 행위자가 어느 쪽인지는 상태머신이 본다. 그래서 서비스 메서드는 Security 도입 전부터 행위자 정보를 파라미터로 받고, 테스트는 행위자를 직접 만들어 넣는다.
- **요청관과 제공관은 역할이 아니라 관계다.** 같은 사서가 어떤 요청에서는 요청관, 다른 요청에서는 제공관이다. 행위자와 요청을 보고 관계를 계산한 뒤, 전환표의 허용 관계와 비교한다. 가족 여부처럼 DB 조회가 필요한 관계는 애플리케이션 계층에서 계산해 넘긴다.
- **"진행 중"의 두 기준은 코드 한 곳에서만 정의한다.** 이용자 기준(중복 신청, 동시 진행 한도)과 자료 기준(자료 배정)은 다르다. 같은 목록이 마이그레이션의 부분 유니크 인덱스에도 있으므로 둘이 항상 같아야 한다.

## 코드 위치

패키지 접두어 `com.hyeon.interlibraryloan`은 생략했다. 세부 파일은 `references/transitions.md` 0절에 있다.

## 전환을 추가하거나 바꾸는 절차

1. **표부터 고친다.** `references/transitions.md`를 먼저 수정하고, 사용자에게 노션 요구사항 정의서도 고쳐야 한다고 알린다. 기존 비즈니스 규칙과 충돌하면 코드를 쓰기 전에 사용자에게 묻는다. 실제 도서관 업무 규칙을 지어내지 않는다.
2. **전환표 코드**에 (현재 상태, 행위) → (다음 상태, 허용 관계)를 추가한다.
3. **부수 효과**를 같은 트랜잭션에 묶는다.
   - 소장 자료 상태 변경 (자료 상태 전환표를 따른다)
   - 상태 이력 한 행 (행위자 유형, 행위자 계정, 사유, 시각)
   - 취소면 취소 정보(사유 코드, 메모). 메모 필수 여부는 취소 사유 코드 테이블 값으로 검증
   - 도착이면 수령 기한, 수령이면 대출 행과 반납예정일. 기한은 그 시점 정책으로 계산해 저장하고 이후 바꾸지 않는다
   - 3단계 이후에는 아웃박스 이벤트 한 행
4. **이용자 표시 단계** 매핑을 확인한다. 이용자는 내부 상태를 보지 않는다.
5. **DB와 맞춘다.** 새 행위면 이력의 행위 CHECK를, 새 상태면 아래 절차를 따른다.
6. **테스트**를 아래 목록대로 쓴다.

## 상태 목록이 바뀔 때

상태 값은 Java enum, CHECK 제약, 부분 유니크 인덱스 세 곳에 있다. 하나만 바꾸면 기동은 되는데 규칙이 조용히 어긋난다.

1. enum에 값을 추가하고, 종료 상태인지와 두 "진행 중" 기준에 속하는지 정한다.
2. `flyway-migration` 스킬로 새 마이그레이션을 만들어 `ck_loan_request_status`를 다시 만든다. 진행 중 기준이 바뀌었으면 `ux_loan_request_item_active`, `ux_loan_request_patron_bib_active`를 지우고 다시 만든다. 이력의 from_status, to_status CHECK도 확인한다.
3. 이용자 표시 단계 매핑에 새 상태를 넣는다.

## 테스트 목록

순수 단위 테스트(JUnit 5, AssertJ, Spring 없음)로 쓴다. `@DisplayName`은 한국어로 쓰고 관련 규칙 ID(BR-xx, FR-xx)를 붙인다.

- **허용 전환**: 표의 모든 행이 기대한 다음 상태로 간다. 기대값은 테스트 안에 직접 적는다. 프로덕션 전환표를 읽어 기대값을 만들면 표가 틀려도 테스트가 통과하기 때문이다.
- **금지 전환 전수 검사**: 모든 (상태 × 행위) 조합 중 허용 목록에 없는 것은 전부 거부된다. `@ParameterizedTest`로 조합을 만든다.
- **관계 검사**: 허용 전환마다, 허용되지 않은 관계의 행위자는 거부된다. "가 도서관 사서가, 가 도서관이 제공관이 아닌 요청을 발송하려 하면 거부"처럼 같은 역할이 관계 때문에 막히는 경우를 꼭 넣는다.
- **부수 효과**: 자료 상태, 이력 행, 취소 정보, 대출 행이 기대대로 생기거나 바뀐다. 반납예정일은 이후 어떤 전환에도 바뀌지 않는다.
- **종료 상태**: 종료 상태에서는 어떤 행위도 허용되지 않는다.

DB 규칙(부분 유니크, 복합 FK)은 단위 테스트로 확인할 수 없다. Testcontainers 리포지토리 테스트나 통합 테스트로 따로 확인한다. 같은 자료를 두 요청이 동시에 배정받으려 할 때 하나만 성공하는지가 대표적인 경우다.

## 체크리스트

- [ ] `references/transitions.md`와 코드의 전환표가 같다
- [ ] 허용 목록에 없는 전환은 거부된다
- [ ] 관계 검사가 역할이 아니라 요청과의 관계로 판단한다
- [ ] 부수 효과가 같은 트랜잭션 안에 있다
- [ ] 상태가 바뀌었다면 CHECK와 부분 인덱스 마이그레이션이 있다
- [ ] 이용자 표시 단계 매핑이 빠짐없다
- [ ] 사용자에게 노션 문서 갱신을 알렸다
